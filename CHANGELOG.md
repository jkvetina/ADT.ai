# Changelog

All notable changes to the public ADT.ai release are recorded here, newest first.

## 0.8.4 - 2026-08-07

- **New: `ut3 -coverage` reports Oracle code coverage for every package in the connected schema — including the ones no test ever reaches.** A report built from coverage data alone can only describe packages that were *executed*, so the package with no test at all — the one you open the report to find — is silently absent from it. `CODE COVERAGE:` therefore leads with the schema's own package list and joins the measurements onto it, and `NO CODE COVERAGE:` is the work list beside it, carrying `PACKAGE` and `LINES` only: a package at 4645 untested lines and one at 91 are not the same problem, and every other column there is constant by construction. **Three cells never render alike** — `-` means nothing was measured, `0` means Oracle instrumented the package and nothing ran it, and `NATIVE` is a `-` with the cause attached — because each calls for a different fix, and collapsing any two puts uninstrumentable code in the same column position as untested code. The run itself goes quiet: the suites still execute, since running the code is the only way Oracle collects block coverage, but the suites roll-up, the per-test rows and the run `SUMMARY:` are suppressed, so a green run is the coverage tables and nothing else — while `ERRORS & FAILURES:` still prints whenever there is something to put in it. **`-name` means one thing in both modes**: it narrows the run, and under `-coverage` it narrows the listing as well. The under-report that follows is real and documented — a package reached only by an excluded suite reads lower than the truth, so the schema's own figures come from `-coverage` with no `-name` — and a pattern matching no suite exits non-zero rather than printing an empty report. `SUMMARY:` closes with a single row, `PACKAGES` / `LINES` / `COVERED` / `COVERAGE`, where **`COVERED` counts source lines that actually ran**. The three figures deliberately do not divide into each other, and every surface now says so: `LINES` counts every package-body source row including the comments and declarations Oracle never instruments, `COVERED` counts instrumented lines that ran, and `COVERAGE` stays covered blocks over measured blocks. A percentage is quantized half-up and prints at one fixed decimal with no `%` sign, so a right-aligned column actually stacks; it blanks when nothing was measured, because a percentage is a claim about collected data, while `COVERED` still reads `0` there — nothing executed is a measured zero. Coverage is read through utPLSQL's own paired `DBMS_PLSQL_CODE_COVERAGE` run rather than started independently, with the run id generated client-side so a concurrent session's rows can never be picked up, and blocks marked by the `COVERAGE` pragma are subtracted from the denominator. See `USAGE/ut3.md`.
- **`ut3`'s `SUMMARY:` gains a `TIMER` column — that suite's own seconds.** It is wall clock around the whole `ut.run` call, not the sum of utPLSQL's per-test times: a suite spends as much of its cost in `%beforeall`, teardown and the round trip as in its assertions, and a column that left those out would not account for the total printed at the foot of the run. It is also the one column a zero does not blank out of — the verdict columns blank theirs because a `0` competes for the eye with a real count, whereas `0.0` seconds is a measurement and an empty cell would claim there was none.
- **`recompile` now says where to start when a schema is full of invalid objects.** A dropped sequence invalidates the package that used it, which invalidates the trigger and the view that used *that* — and `INVALID OBJECTS` printed the whole crater as one flat list where every row looked equally like a place to begin. A new always-on `ROOT CAUSES` section separates the objects that are broken from the ones that are merely downstream, ranks the former by how much of the list they explain, and adds a `BLAST` column counting what clears transitively. Three signals feed it, because no one of them is sufficient: **the error text**, which usually names the culprit, and where the named object being itself invalid is what separates a knock-on from a root; **the stored source** at the error's own line and position, for the errors that name nothing (`ORA-00942` reports no object, and Oracle records no dependency row for a reference that never resolved); and **the offline dependency mirror** in `config/dependencies.db`, which connects invalids whose errors point at nobody — a missing or stale mirror degrades the ranking rather than failing the recompile. `CAUSE` keeps three fixes apart that a flat list blurs into one: `SOURCE` (its own text does not parse), `MISSING` (something it needs is gone) and `GRANT` (it exists and this schema cannot see it) — recompiling forever never fixes the last of those, and reading it as `MISSING` sends you hunting for an object that is already there. The section reads **after** the list it ranks, so the verdict arrives behind the evidence rather than pointing forward at rows nothing has introduced yet. **Compile errors are now a per-object list rather than a table:** one `<OBJECT TYPE>.<OBJECT NAME>` stanza, then `<line>.<pos> <message>` per distinct error, wrapped under a hanging indent and never truncated — the old table spent its widest column on a cross-reference id and rendered `…object SSO...`, which names nothing to grant. Oracle's cascade rows (`Statement ignored`, `SQL Statement ignored`, `Compilation unit analysis terminated`) are dropped from the list and discounted from the ranking, so the noisiest object no longer outranks the most upstream one, and a message repeated at several positions prints once at its lowest one. The `ID` column is gone from the whole report — every section names the object instead, object type included, since a schema can carry `UT_UTILS` as both a `PACKAGE` and a `PACKAGE BODY` with different errors that a bare name would merge. A stored newline inside an error message can no longer break the layout, and each verdict heading carries exactly one blank line above it.
- **`export_db -by` and `-my` stop claiming a recency they never measured, and a new optional `audit.changed_at` column gives them one.** Both filters were documented as exporting the objects a developer **last** changed; the query behind them selected any object that developer had ever touched, with no ordering at all. An object you touched last week and a colleague rewrote yesterday exported under `-my` looking exactly like one that was still yours — the failure mode the filter exists to prevent. A DDL log with no timestamp column genuinely cannot answer the question, so the fix is a fourth optional `audit:` key rather than a silent guess. With it configured, the query reports each object's **latest** author, and two things follow: an object you worked on that somebody else changed afterwards is **still exported** — dropping it would silently lose work you really did — and its export row carries the later author in square brackets, `APP_ORDER_PKG [SCOTT]`. And `-recent` finally reaches the audit source, so `-my -recent 1` means "changed today by me" instead of "changed within a day AND I once touched it", which is two unrelated sources silently ANDed. Without `changed_at` nothing changes, no row is marked, and the documentation now says *has changed* rather than *last changed*. `USAGE/export_db.md` documents the expression a project's DDL trigger should record, and why a proxy session must record it explicitly: in a proxy session `USER`, `ORA_LOGIN_USER` and `SESSION_USER` all report the proxied schema, so authorship that was never written down cannot be recovered afterwards by any query.
- **`export_apex -rest`: a dead SQLcl session can no longer finish as a successful export, and the export now has a deadline.** `WHENEVER SQLERROR EXIT FAILURE` has guarded every connect block since 0.8.2, but it can only trap *SQL* errors and `SP2-0640: Not connected` is a client-level message — so a connect that left no session behind never fired the guard: SQLcl ran the whole script against nothing, answered every statement with `SP2-0640`, and exited **0**. The exit code cannot see that failure, so it is now read out of the transcript and raised whatever the exit code says, which also makes the re-registration retry fire for the failure it was written for (it was keyed on a non-zero exit, on the assumption that a missing connection name fails structurally — it does not). **The whole SQLcl transcript, already secret-scrubbed, now rides the error** instead of a single regex-picked line: `SP2-0640` is reliably the consequence of a connect that failed some lines earlier, and that line was being discarded, so escalations arrived with no cause attached. New `rest_timeout_seconds` (default 60) bounds the REST export, which could previously sit for as long as SQLcl liked with nothing on screen but a crawling progress bar. And a failed export row is completed with `FAILED` before the error banner — the crawling row is rewritten in place with no trailing newline, so abandoning it there meant the next thing printed was spent terminating it and `UNEXPECTED ERROR` landed flush against the progress bar.
- **`export_apex -files_ws` exported the same workspace files once per application.** 0.8.3 moved `-rest` out of the per-application loop because REST services belong to the schema — they land under `apex/workspace/`, a path with no app id anywhere in it. `-files_ws` writes through the same workspace root and was left in the loop, so a run over N applications re-fetched and rewrote the identical files N times, and a schema hosting no application exported none of them at all. Both halves of that fix now apply to it. The two schema-level slices also render among the first application's ordinary export rows rather than spending a header and a blank line on a single row; the separate `SCHEMA <name>, EXPORTING:` header survives in exactly one case — a schema with **no** application, where there is no block for the rows to sit under. The estimate still comes from the workspace timing slot, because the row is carried by an application but the work is not that application's.
- **The APEXlang skip row prints only when `-apexlang` was asked for by name.** `APEXLANG EXPORT SKIPPED, NEEDS APEX 26.1` answers "where is my APEXlang export?" — a question only the user who typed `-apexlang` or `-apx` asked. Under `-all` nobody named the format, so on every pre-26.1 instance the line reported the absence of something never requested, on every run. It is silent there now; skipping is unchanged either way, and `-readable`'s own 26.1 gate has always been silent, so the pair finally reads consistently instead of one of them carrying a special case. The row also states the requirement rather than the finding — the instance's APEX release is already in the connection block a few lines above — and drops its dotted leader, since dots carry the eye across to a result that was measured and this format never ran. `USAGE/export_apex.md` no longer credits `-all`'s non-failure to that note printing.
- **Tables no longer wrap on an 80-column terminal, and every section header ends with `:`.** Each cell was padded to its column width and given a three-space gutter, the last column included, so an unstripped row ran three characters past its visible content — nine on the header row, whose last cell is shorter than the column. At 81 characters against an 80-column terminal that invisible tail wrapped and printed as a blank line under every single row: the same table read as perfectly aligned one column wider and shredded one column narrower, which is exactly how it was reported. The completed line is now stripped, alignment is untouched — a cell is placed by what sits to its left, never by spaces to its right — and tables fit the 78-column width every other renderer already uses. Half of the tool's 102 titled sections disagreed with the other half about whether a header closes on a colon, with no rule to consult; they all carry one now, and the module banner — the one exception — reads `APEX DEPLOYMENT TOOL - EXPORT_APEX`, underlined across its full width. **A value or a count folds into the header phrase instead of trailing the colon**, because the dashed rule is sized to the header's message and anything after the colon sat past the end of its own underline: `EXPORTING OBJECTS: (61)` is now `EXPORTING 61 OBJECTS:`, `REFRESHING: ICT_OWNER` is now `REFRESHING ICT_OWNER SCHEMA:`, and `OBJECTS CHANGED SINCE 2026-08-04 07:29:54 (LAST EXPORT):` is now `OBJECTS CHANGED SINCE LAST EXPORT AT 2026-08-04 07:29:54:` — a sentence whose subject arrives first. A count already in parentheses keeps them and takes the colon after: `APEX CALLERS (5):`.
- **`dependencies -refresh`'s locked-object skip line is indented and unqualified:** `    SKIPPED LOCKED PACKAGE AUTHMAN`, where it read `SKIPPED LOCKED PACKAGE.AUTHMAN` hard against the left margin. Two defects in one short line — alone in the whole refresh it started at column 0, so it read as a section rather than as the interruption of the row above it; and `TYPE.NAME` is the shape ADT prints for an *owner*-qualified name, which invited the reading that `AUTHMAN` lives in a schema called `PACKAGE`. The line itself stays, and `USAGE/dependencies.md` now says why. It is tempting to read it as noise on a command that feels read-only, but `-refresh` is not read-only: it recompiles every VALID PL/SQL object still missing full PL/Scope, because the identifier dictionary is where the graph comes from, and a recompile is DDL that needs an exclusive lock. A skip therefore means that object's edges in `config/dependencies.db` were **not** refreshed while the command still exits `0`, and deleting the line would make a silently incomplete graph indistinguishable from a complete one.

## 0.8.3 - 2026-08-05

- **New `ut3` command — it runs the connected schema's utPLSQL test suites, and treats every shape of dishonest green as a failure.** `adtai ut3` with no arguments runs every suite in the schema; `-name` takes repeatable Oracle `LIKE` patterns over the suite package name, resolved by the same implementation `recompile -name` uses, so a pattern selects identically across commands. A package is a suite only when both halves agree: its name ends in `_UT` **and** utPLSQL has parsed it as a `%suite`, so production code can never be swept into a test run by a loose pattern. Discovery reads the data dictionary and utPLSQL's own annotation cache, because each is the only place one half of that answer exists — and `-refresh` rebuilds the annotation cache first, which is the fix for a suite compiled since the last run reporting `NOT A SUITE`. **The exit code is the deliverable**, because utPLSQL does not raise when a test fails: a failed or errored test, a report that came back empty or unparsable, and a run where nothing matched at all are all non-zero. A zero-test run is a failure rather than an empty pass — an empty green run is exactly what a vanished suite looks like from outside. The output is one grid: `UNIT TESTS SUITES:` rolls up what is about to run — suite package and test count — and prints its header even when the list is empty; `TEST RESULTS:` then prints *as the run proceeds*, one block per suite, each row carrying the test's procedure name rather than its `%test` description, so a failing test can be searched for in the package source; every non-passing test gets a wrapped stanza under `ERRORS & FAILURES:` headed `<STATUS> > <PACKAGE>.<TEST>`; and `SUMMARY:` repeats the suites table with `PASSED` / `FAILED` / `ERRORED`, blank wherever a count is zero. Packages print A-Z and tests in the order the package specification declares them. A `_UT` package that is INVALID or holds no parsed `%test` is ignored — it is not a suite, so it is listed nowhere and fails nothing on its own, while the vanished-suite case it used to cover is still caught by the zero-test rule. `-silent` reduces a green run to the banner, summary and timer, and deliberately keeps `ERRORS & FAILURES:` — a quiet mode that hides the reason a run went red is the inversion of what quiet is for. See `USAGE/ut3.md`.
- **SQLcl is launched without `ORACLE_HOME`, so it stays on the thin driver instead of asking the JVM for an OCI library it can never load.** Every SQLcl-backed command — `export_apex -rest` among them — died on macOS with `Connection failed … URL = jdbc:oracle:oci8:@host:1521/SVC / Error Message = no ocijdbc23 in java.library.path`, and the message points at a library that is present and correct, so the obvious readings are all wrong: it is not a missing Instant Client and not a version mismatch. SQLcl's launcher takes an `ORACLE_HOME` containing an `ocijdbc` library as "the thick driver is available" and hands the JVM the OCI libraries through `DYLD_LIBRARY_PATH` — which macOS strips when exec'ing a protected binary, and both the launcher and the JVM are protected. The OCI URL is therefore unsatisfiable by construction on that platform, for every client version, and no configuration reaches it. ADT.ai created the condition itself by exporting `ORACLE_HOME` for python-oracledb's thick mode; SQLcl is a Java program on the thin driver and needs no client libraries at all. The SQLcl child process is now given an environment with `ORACLE_HOME` removed and everything else intact — `PATH` still finds the launcher, `TNS_ADMIN` still resolves aliases, wallet connects are unchanged — and the parent's environment is never touched, so thick mode still works for every command that connects through python-oracledb.
- **A schema name resolves case-insensitively, so the same project stops working in one command and failing in another.** An Oracle schema name is a case-insensitive identifier, but the connection lookup matched the YAML key exactly — and ADT.ai reaches it both with what you typed in the connection file and with a name a command derived from a folder and upper-cased. So a connection file keyed `ict_owner` served `-schema ict_owner` and failed for the same schema arriving as `ICT_OWNER`, reporting `Schema not configured: DEV.ICT_OWNER` while printing `Available schemas in DEV: - ict_owner` directly underneath — which reads as a broken connection file rather than as a lookup rule. **The exact key still wins**, so a file deliberately carrying two casings keeps both, and the resolved connection reports the key as the file spells it rather than as the caller happened to type it.
- **`file_crlf` now decides the line ending of exported files instead of merely adding to whatever the database already carried.** Reported from Windows: configuring LF still produced CRLF files, so the setting read as ignored. It was not ignored — Python translates `"\n"` on write and never touches a `"\r"` already in the string, so LF mode passed an existing `"\r\n"` straight through and CRLF mode rewrote the `"\n"` inside it into `"\r\r\n"`. Oracle returns the stored source verbatim, and anything ever loaded from a Windows client carries CRLF in it, so both modes produced CRLF on exactly the objects the setting exists for. Every incoming `\r\n` and lone `\r` now collapses to `\n` before the configured ending is applied, so the configured ending is the only ending on disk in either mode, whatever the database returned. **`export_db`'s unchanged-file check was wrong the same way** — it compared raw DDL against a universal-newline read, so a CRLF-carrying object never matched and was rewritten on every single export; it now compares the normalized content the writer would produce. The blast radius was all three exporters, not just the reported one: `export_db` DDL, `export_apex` split/full/APEXlang payloads, and `export_data`'s generated merge script, where a `VARCHAR2` value holding CRLF was inlined into SQL. The two byte-faithful exceptions are unchanged: raw LOB sidecars and the CSV handle still mirror stored values exactly.
- **`export_apex -rest` is a schema-level export again, so a schema with no APEX application stops exporting nothing at all.** REST services belong to the schema — they land in `apex/workspace/rest/`, a path with no app id anywhere in it — but the export ran inside the per-application loop. Two consequences, and the worse one is silent: a schema that publishes REST services but hosts no APEX application skipped the export entirely, printing nothing and exiting `0`; a schema with N applications ran the identical schema-wide export N times over the same files, showing N REST progress bars for one set of artifacts. `-rest` now runs once per schema after the application loop, under its own `SCHEMA <name>, EXPORTING:` header, timed under the workspace slot the way `-files_ws` already treats app 0, and skipped in `-recent` report-only mode like every other export.
- **An unresolved `{$...}` placeholder in `path_objects` is now a config error instead of a folder name.** `path_objects` resolves exactly two placeholders — `<schema>` and `<object_type>` — and the old ADT `{$NAME}` syntax is not among them, so a template such as `'{$INFO_SCHEMA}/database/'` passed through the resolver verbatim and the export built a real directory literally called `{$INFO_SCHEMA}`. Nothing failed, nothing warned, and the run reported success; on one project 851 files accumulated in that folder, shadowing the tracked tree. This is the copy-paste a migrating project makes rather than an exotic misconfiguration — old ADT ships that value as a commented example — so it is now a loud error naming the token, the key, the offending value, and the placeholders that *are* supported, raised everywhere the template is resolved so no command keeps writing into the placeholder folder after another refuses. It is deliberately narrow: only `{$...}` in `path_objects` is treated as unresolved, and the token stays live syntax in the keys that substitute their own. The guard **never cleans up** — a `{$INFO_SCHEMA}/` tree an earlier run created is left exactly where it is for you to delete, because removing exported source is not a config guard's call. ADT.ai's own shipped `config/config.yaml` stops carrying the same trap: `apex_schema` is now the plain `'APEX'` the code was already falling back to. Finally, a config that was found but holds an unusable value now reports `CONFIGURATION INVALID` rather than `CONFIGURATION NOT FOUND`.

## 0.8.2 - 2026-08-03

- **A SQLcl session that never connected no longer reports success.** `export_apex -rest` could run its progress bar to 100%, write no files, and say nothing — while the connection file was rewritten with a SQLcl connection name and credential fingerprint for a stored connection that had never been created. Deleting those two lines by hand and re-running just wrote them straight back, so the failure could not be cleared from the outside. Two causes, both fixed: SQLcl continues after an error by default, so a script whose `connect` failed ran on to its exit and returned success — a dead session and an empty result were the same thing to the caller; and the SQLcl process inherited the terminal's input, so a failed connect fell back to a username prompt that the captured output swallowed, and the run waited forever on input nobody could see it asking for. Every generated connect now aborts the script on failure, and the SQLcl process is given no input to wait on, so a bad credential or an unreachable host fails immediately with the Oracle error on screen. The connection name and fingerprint are recorded **only after the run that registered them actually succeeded**, so what the connection file claims is now something that happened. **Behaviour change:** a failed connect that used to look like an empty result is now a non-zero exit carrying the SQLcl message, on every command that opens a SQLcl session.
- **`export_apex -rest` tells an empty export apart from a failed one.** A schema that genuinely publishes no REST services still exports successfully and leaves an empty folder; a REST export that reported an Oracle or SQLcl error now fails naming that error, instead of writing nothing and completing as though there had been nothing to write.
- **`recompile` shows what the run actually repaired.** Every number in OBJECTS OVERVIEW was read *after* the recompile, so a run that fixed seventeen package bodies printed exactly what a run that fixed nothing printed — there was no visual clue that anything had been repaired. A new `VALIDATED` column sits immediately before `INVALID`, so the two read as a pair: what the run fixed, and what it could not. It counts objects by identity rather than as a before-and-after difference, because recompiling a package spec invalidates its dependents — a run that repairs one object and breaks another leaves the invalid count unchanged, and a plain difference would report that repair as nothing having happened. A zero renders blank exactly as `INVALID` already does, so only real repairs draw the eye.
- **Documentation corrected: no sample connection file ships with the tool.** `USAGE/connection.md` described a template connection file as shipped and created for you; connection files hold credentials, so `doctor -init` writes none. `connection -create` is the bootstrap path.

## 0.8.1 - 2026-08-03

- **Breaking — a connection file no longer renames the folder a schema exports into.** The `export.subfolder` key and its `-subfolder` flag are gone: a schema's objects always land under the schema's own lowercased name, so where an object file lives is decided by `path_objects` alone rather than by a second, invisible setting that made the folder stop matching the schema with nothing on disk to say why. `export:` carries exactly two keys from here — `prefix` and `ignore`, the filters that decide *what* is exported. **Upgrading needs no edit**: a leftover `subfolder:` line in an existing connection file is read as ordinary data and ignored, so it can be deleted whenever convenient. Passing the removed flag exits `2` with `unrecognized arguments` rather than being silently accepted.
- **`connection -create` now fills blank export placeholders instead of quietly doing nothing.** The sample connection file every project starts from ships its export block pre-seeded and empty, and an existing key was treated as a value to preserve — so `adtai connection -create -env DEV -schema CORE -ignore 'JOB%' -go` wrote nothing, previewed the unchanged value, and exited `0`. A no-op reported as success, with a hand-edit of the YAML as the only way to set an export filter at all. A blank value — absent, empty, or whitespace — is now recognised as the placeholder it is and filled; a value that is genuinely set is still preserved, so `-create`'s "fills only missing fields" contract is unchanged for anything already configured.
- **`connection` previews no longer print stored secrets.** The default preview (no `-go`) reused the loaded environment verbatim, so it printed every sibling schema's passwords and the wallet passwords to stdout — exactly the surface that lands in shell history and terminal transcripts. The preview is now a structural copy with every secret key stripped, while the file it applies keeps them; a `-like` clone no longer carries an encrypted wallet password into a new environment either.
- **`dependencies -refresh` opens its connection the same way every other command does, so `config/STARTUP.sql` runs there too.** On a schema whose DDL trigger requires a client identifier the refresh did not degrade, it failed outright with `ORA-20990` — and it is a prerequisite of other work, so the failure propagated. Every command in ADT.ai now builds its database connection through a single shared function, so session setup — the client-identifier block, `STARTUP.sql`, the shared `DDL_LOCK_TIMEOUT` — reaches all of them, and anything added to what a connection does is inherited everywhere instead of being wired up eleven times.
- **A disabled trigger now exports as a file that actually runs.** Oracle reports a trigger's disabled state by appending `ALTER TRIGGER "OWNER"."NAME" DISABLE;` to the DDL — but *inside* the `CREATE TRIGGER` block, above the terminator. `export_db` stripped only the `ENABLE` form, so the whole file went out as one statement with an `ALTER TRIGGER` buried after `END;`, and raised `PLS-00103` the moment anyone ran it. Every disabled trigger in every export was non-runnable. The statement is now lifted out and re-emitted below the terminator, verbatim as the database wrote it with a blank line on each side, so the file is a `CREATE` block terminated by `/` followed by a plain statement terminated by `;`. `ENABLE` is still dropped outright — it is the default state and re-asserting it says nothing.
- **`export_db` puts a trigger's `FOR EACH ROW` on a line of its own.** Oracle hands the trigger header back exactly as the developer typed it, so the one clause that decides whether the body runs per row or per statement could sit buried at the end of whatever line its author happened to write, and every schema read differently for a reason that has nothing to do with the trigger. The clause is now split onto its own line, inheriting the surrounding indentation, with any trailing `WHEN (...)`, `DECLARE`, or `BEGIN` pushed to the next line. Only the header is touched: past the start of the body those three words are data, statement-level triggers are unchanged, an already-split header is a no-op, and the body itself is still preserved verbatim — so repeated exports stay byte-identical.
- **`recompile` no longer has a LOCKED OBJECTS report.** It read `gv$` dictionary views, and ADT.ai connects as the application schema it maintains, which holds no `SELECT` on them — that grant is a DBA decision, not a misconfiguration a deployment tool can correct, and no unprivileged view answers the same question. So on a normal setup the query was issued, failed, and was swallowed once per schema per run, with two lines of `ORA-00942` noise sitting above every report. The report is therefore removed rather than left to fail quietly. **Nothing is lost operationally**: a lock wait is already bounded by the shared `DDL_LOCK_TIMEOUT`, and an object that stays locked surfaces as its own compile error under `INVALID OBJECTS` — the table only ever named who was holding it. `-mviews` keeps its lock pass as its one retained report.
- **A corrupt cache or hand-edited config file now degrades with a warning instead of killing the run.** A YAML syntax error in a generated cache (`config/recent.yaml`, `apex_timers.yaml`, `apex_apps.yaml`, …) or in `config/IDENTITY.yaml` used to cost the whole command with a raw parser traceback; both loaders now warn and continue empty, a malformed `connections.yaml` reports through the friendly connection banner, and an unreadable README no longer aborts `doctor`. In the same hardening pass: a foreign-key tree walk survives chains deeper than Python's recursion limit, `search_repo -restore` prints a `COULD NOT RESTORE:` section instead of letting an incomplete restore look finished, blank `groups.yaml` entries are reported rather than silently dropped, and a control character in a commit subject or author name can no longer truncate a cached record.
- **Documentation corrected against the code.** `USAGE/recompile.md` marks `-scope`/`-warnings` repeatable (they always were), `USAGE/search_repo.md`'s argument table gains the `Repeatable` column its siblings carry, and the discovery report filename reads `<YYYY-MM-DD--HH-MI>.md` everywhere.

## 0.8.0 - 2026-07-28

- **New `validate` command — check an exported APEXlang folder before anything tries to import it.** `adtai validate` runs the APEXlang compiler over the `apexlang/` trees written by `export_apex -apexlang` and exits non-zero when the compiler reports anything, so it works as a deploy or CI gate. **It never connects to a database** — no environment, schema, or credentials — so it runs from any checkout and in CI. Targets resolve three ways, and they combine: `-input` takes a folder, a zip, or a single `.apx` file; `-app` is repeatable and resolves offline to that application's export path; and a bare run validates every `apexlang/` folder under the configured APEX root, which makes `adtai validate` the natural follow-up to an `-all` export. Compiler messages print as a per-message list — `file:line:col` on its own line, type and message beneath — wrapped rather than truncated, because the message names the file that is missing. Warnings are listed but never fail the run. A folder holding no APEXlang files, an input path that cannot be found, a requested application with no export on disk, and output this version cannot parse are all non-zero: a run that checked nothing is never reported as a pass. Static-file payloads are linked into place before compiling, so an application that owns static files validates against its real files without the repository ever holding a second copy of them. See `USAGE/validate.md`.
- **`export_apex` gains a ninth format: `-apexlang` (alias `-apx`)**, which exports APEX 26.1's APEXlang `.apx` source as a whole-application folder tree under `apexlang/` in the application folder, and joins `-all`. The layout is what APEX emits — `application.apx`, `pages/`, `shared-components/`, `workspace-components/` — written verbatim, with none of the SQL export's postprocessing: `.apx` is compiler input, not something to decorate. The folder is recreated on every export, so a component deleted in App Builder cannot survive as a stale `.apx`. APEXlang is a whole-application format in this version — `-page`, `-component`, and `-recent` never filter it, and an APEXlang run never advances a `-recent` watermark. Below APEX 26.1 the row completes as `SKIPPED` rather than failing, so an `-all` run against an older instance degrades instead of breaking; on 26.1 and above, where the readable-YAML format was folded into APEXlang, a requested `-readable` slice is skipped. Static-file payloads are deliberately not written into `apexlang/` — `-files` remains the single static-file channel, so the repository holds one copy of each file — which makes `apexlang/` a source and review surface, readable in Git and editable by hand or by an AI tool, rather than a directly importable artifact.

- **`export_apex -deep` is now part of the public surface.** Combined with `-page`, it also exports the components recorded for the selected pages in `config/dependencies.db` — LOVs, lists, authorization schemes — so a page export carries the shared components that page actually uses instead of just the page itself. It reads the dependency mirror, so run `dependencies -refresh` first; `-deep` without `-page` is rejected.
- **ADT.ai now fills in its own environment when the calling shell never ran your startup file**, so a command invoked from an AI coding tool, an editor, or any other non-login shell stops failing on a missing `ADT_KEY` or `ORACLE_HOME`. When either `ADT_ENV` or `ORACLE_HOME` is unset, ADT.ai reads your shell startup file and fills in only the variables it knows about, and appends `$ORACLE_HOME` and its `sqlcl/bin` to `PATH`. **A variable already present in the environment is never overwritten**, so an explicit export, a CI variable, or a one-off `ADT_ENV=PROD adtai …` always wins; when both sentinels are already set, nothing is read at all. Every failure mode is soft — a missing file, an unreadable file, or a shell that will not run leaves the environment exactly as it was rather than failing the command. POSIX only; on Windows it is a no-op. `doctor` gains a `HYDRATED` row naming the variables that were filled in and the file they came from, and `ADT_KEY` is hydrated but never printed.

ADT.ai now writes LF everywhere by default and CRLF everywhere when `file_crlf: true`, including CSV row terminators. - Changed `-reveal` to collect all matching applications first and then derive the workspaces and owners summary tables from those actual results, so narrowing with `-app` or `-schema` narrows the summary sections too. Application-section headers now include the workspace name (`APEX APPLICATIONS: <WORKSPACE>, <SCHEMA>`).

## 0.4.4 - 2026-06-13

- Fixed a batch of `export_db` DDL formatting issues so exported files match a clean, readable layout on real `DBMS_METADATA` output: views (simple, compact comma-packed, mixed quoted/unquoted, and CTE select lists), expression indexes, table columns, `INTERVAL` suffixes, `INMEMORY` clauses, schema qualification, and TYPE / TYPE BODY drop preambles.
- Changed `export_db` to consolidate dedicated PK/UNIQUE indexes: when Oracle exports a primary-key or unique constraint as a separate `CREATE [UNIQUE] INDEX` plus `ALTER TABLE ... ADD CONSTRAINT ... USING INDEX`, the constraint is now folded back inline on the table so it reads as if the table were created in one clean statement. Table constraints are ordered deterministically — PRIMARY KEY, then UNIQUE, then FOREIGN KEY, then CHECK, alphabetically by name within each group — while column lines keep their source order.
- Added a `<table>.fix.sql` companion file beside any table whose index-backed constraints were folded inline. It holds the recovery script (`DROP CONSTRAINT` / `DROP INDEX` / `ADD CONSTRAINT`) that rebuilds the original dedicated-index arrangement, so the clean table export loses no information. The companion is regenerated when folding happens and removed when a table no longer has index-backed constraints.
- Changed `export_db` sequence DDL to drop Oracle's default ascending `MAXVALUE` (28 nines), matching how column DDL already strips it, while preserving explicit non-default maxvalues such as `MAXVALUE 999999999999`.

## 0.3.0 - 2026-06-12

- Added four new commands — `recompile`, `rebuild`, `search_repo`, and `discovery` — each with its own `USAGE/<command>.md` reference.
- `recompile` recompiles a schema's invalid objects with an objects / invalid-objects overview, supports `-force`, `-scope`, and name filtering, builds the right `ALTER ... COMPILE` flags (native vs interpreted, optimize level, PL/Scope, warnings), retries in reverse dependency order on reconnect, runs a final re-check, and exits non-zero when objects remain invalid.
- `rebuild` builds a fast per-branch Git commit cache (one file per branch) with a count-first pass and progress ETA; its read-only `-reveal` branch inspector filters by name words, `-my`, and `-since` with a `-limit` cap, and can `-switch` the working tree to a listed branch; incremental runs resume from the cached tip so large branches refresh in seconds.
- `search_repo` searches Git history fast off the `rebuild` cache — by summary terms, file path, database object type/name, author, commit or branch, and date windows (`-since` / `-until`) — printing newest-first with optional changed-file rows, and can restore matched historical file versions.
- `discovery` is a safe, read-only `SELECT` explorer aimed at AI-assisted querying: a static validator accepts only a single `SELECT` per statement (rejecting DML, DDL, PL/SQL, multiple statements, and comment-smuggled commands), every accepted query runs inside a rolled-back `SET TRANSACTION READ ONLY` session, and results render to the console (`-nolog`) or to a per-run Markdown report.

## 0.2.0 - 2026-06-12

- Added the `export_apex` and `export_data` commands and shipped an MIT `LICENSE` so the public repo is safe to use and distribute.
- `export_apex` exports APEX applications in every format — full, split, readable, embedded, REST, application files, and workspace files, with `-all` running them together — using stable output paths and post-processing; its `-reveal` inventory lists matching workspaces and applications across every configured schema, persists application / developer / timing metadata for repeatable exports, reports recent component changes (`-recent`, `-by`), and can override `p_release` (`-release`) for upgrade recovery.
- `export_data` exports table data to CSV with configurable delimiters, ignored columns, and primary/unique-key row ordering, applies global and per-table `where` filters, and generates DATA MERGE SQL with batched insert / update / delete blocks.
- Shared connection handling improved for both commands: Oracle wallet zip archives are auto-extracted before connect, and database-connection failures print a concise, actionable message (with the full traceback available under `-debug`).

## 0.1.0 - 2026-06-12

- First public release, shipping the `export_db` and `doctor` commands.
- `export_db` exports an Oracle schema to a clean, version-controllable file tree — tables, views, materialized views, indexes, sequences, synonyms, types, packages, procedures, functions, triggers, jobs, grants, and comments — normalizing raw `DBMS_METADATA` output into a stable, readable layout that compares cleanly from one export to the next.
- `export_db` scope and filtering: `-type` and `-name` filters with `%` / `_` SQL-style wildcards and comma-separated values, `-recent` for recently changed objects, and multi-schema exports (default schema lists, comma-separated `-schema`, `%` schema patterns) into the database-first layout `database/<schema>/<object_type>/`.
- `export_db` repository hygiene: `-delete` clean exports, detection and removal of stale object files no longer backed by the database (dry-run stays read-only), in-place updates of nested subfolders, clean `Ctrl+C` handling, and a `-silent` mode for agent-driven runs.
- `doctor` runs local environment health checks for Python, Git, Java, SQLcl, `oracledb`, Instant Client, `PATH`, `JAVA_TOOL_OPTIONS`, and the ADT-compatible environment variables.
- Foundations shared by every command: external connection files and wallets resolved from outside Git (kept out of the repo), automatic wallet extraction before connect, and a consistent console contract — banner, connection block, progress, then a `TIMER` footer.
